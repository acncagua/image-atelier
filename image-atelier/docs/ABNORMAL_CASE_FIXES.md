# 異常系4件の修正・検証

2026-09-12。対象: e459c7fの後の現行実装。報告された4件を修正前の自動テストで再現し、修正後にモックと障害注入で確認した。**今回の外部画像API呼び出しは0回**。

## 1. 取消成功後の送信を禁止

取消と送信開始の両方をStore.update_queuedに集約した。共有ロック内で最新のジョブを読み、「待機中」の場合だけ状態を変更して永続化する。ワーカーはこの変更に成功した場合だけ外部処理へ進む。画像読み込み前の古いスナップショットは送信状態の書き戻しに使わない。送信前失敗と競合する取消についても、取消状態を維持する。

テストは画像読み込みをイベントで停止し、その間に取消APIを呼ぶ方式。修正前は取消成功後に送信処理が1回呼ばれた。修正後は0回で、状態は取消・予約0のまま。逆に送信開始が先に成立した場合は取消成功を返さず、送信は1回だけとなる。

## 2. 保存できない登録は、確認経由でも送信しない

すべてのPOST経路の直前に、同じIDと固定入力のIndexedDB保存を必須にした。404照会後も同じ保存処理を通る。保存拒否のfalseも失敗として扱う。初回保存に失敗した場合は「保存失敗・未送信」、以前のPOSTがあり得る場合は「送信結果が未確認」と区別する。

保存障害が続く状態で確認操作を2回行う再現試験では、修正前にPOSTが2回発生した。修正後は0回。保存が復旧した後には、元のIDと入力で1回だけ送信できる。保存世代は単調増加させ、短時間の受付処理で新しい状態が古い世代と判定されないようにした。

## 3. 一時的な画像取得失敗で下書きを上書きしない

画像の不存在は404で返す。下書きの画像復元は404だけを欠損として扱い、503・通信切断・その他の取得不能では復元を中断する。画像の読み込みが完了するまで、編集状態を適用せず、自動保存と離脱時のフラッシュも停止する。元の下書きと画像IDはそのまま保持する。

「下書き復元を再試行」からページを再読み込みし、通信復旧後に再取得できる。実際の404で回復できない画像については、従来どおり原データをアーカイブに保持し、警告を表示する。

隔離モック画面で画像取得APIへ503を注入し、復元停止の表示を確認した。障害中に再度読み込んだ後でも、障害解除・再試行で編集対象と結果画像の両IDが障害前と一致した。新しい生成ジョブは作成していない。

## 4. 書き出しを完了後に確定し、不完全ファイルから復旧

書き出しは同じフォルダーの一時ファイルへ行い、flush/fsyncを完了してから最終名として確定する。Windowsでは既存先を置換しないrename、他OSでは新規のハードリンクを使い、並行書き出しでも正常ファイルを上書きしない。

既存ファイルが期待したPNGと異なる場合は、そのファイルを保持し、`_recovered_<内容ハッシュ>`付きの別名へ書き出す。不完全ファイルと正常だが内容の異なるファイルのどちらも破壊しない。再処理を繰り返すと同じ復旧ファイルを再利用する。書き出し済みパスが履歴に記録されていても実体の一致を確認し、不完全な場合は書き出し工程をやり直す。

fsync失敗時に最終ファイルが作られないこと、既存の部分PNGからの復旧、正常な別画像の保持、8並行書き出しの同一ファイルへの収束、キャッシュ済みパスにある不完全ファイルの復旧をテストした。
